# Specification: LLM Provider Security

## Purpose
Call the LLM providers and internal services safely: validated TLS, pooled HTTP clients for per-tenant models, tenant keys never sent to another provider, a platform-owned fallback, an authenticated internal gRPC channel, and typed errors without provider details.

## Requirements

### Requirement: Tenant Credentials Are Only Sent to Their Own Provider
A tenant's stored LLM API key SHALL only be sent to the provider and endpoint configured for that key. The fallback model SHALL use platform credentials from configuration (`Ai:Fallback:*`). The fallback SHALL only be triggered by HTTP 429 from the provider (anywhere in the exception chain), on the non-streaming path or, when streaming, before any text was produced.

#### Scenario: Quota exceeded with fallback configured
- **WHEN** a tenant configured with provider `google` and its own key gets HTTP 429 and `Ai:Fallback:ApiKey` is set
- **THEN** the system SHALL retry against the fallback provider using `Ai:Fallback:ApiKey` and append a notice to the answer
- **AND** the request to the fallback endpoint SHALL NOT contain the tenant's Google key

#### Scenario: Quota exceeded without fallback configured
- **WHEN** the provider answers 429 and `Ai:Fallback:ApiKey` is empty
- **THEN** the system SHALL return the typed error `LLM_QUOTA_EXCEEDED` to the client
- **AND** SHALL NOT call any other provider

#### Scenario: Non-quota error containing the word "limit"
- **WHEN** the provider fails with a non-429 error whose message contains "limit" (e.g. "context length limit")
- **THEN** the system SHALL NOT trigger the fallback path
- **AND** SHALL report `LLM_UNAVAILABLE`

### Requirement: TLS Certificate Validation
Outbound HTTP clients to LLM providers and object storage SHALL validate TLS certificates. A certificate-validation bypass for LLM clients (`Ai:Http:AllowInsecureTls`, `false` by default) SHALL only be honoured in the Development environment.

#### Scenario: Production call with an invalid certificate
- **WHEN** an LLM provider endpoint presents an invalid certificate outside Development
- **THEN** the call SHALL fail with a TLS error before any API key is transmitted

#### Scenario: Insecure flag outside Development
- **WHEN** `Ai:Http:AllowInsecureTls=true` is set in a non-Development environment
- **THEN** the application SHALL refuse to start

### Requirement: Authenticated Internal gRPC
The API's commands to the Go scraper (`ScraperCommandService`, `GoScraper:GrpcUrl`) travel over plaintext HTTP/2 inside the internal network and SHALL carry the shared key in the `x-internal-key` metadata (`Internal:GrpcApiKey` in the API, `INTERNAL_GRPC_KEY` in the scraper, generated by the AppHost). The API's `FilterConfigService` SHALL reject calls without a valid key; the key is required at startup in Production, and a missing key is only tolerated in Development. The scraper's calls to the API SHALL use TLS when the target is `https://`.

#### Scenario: Call without the key
- **WHEN** a client calls the API's filter gRPC service without `x-internal-key` or with a wrong value
- **THEN** the call SHALL fail with `Unauthenticated`

#### Scenario: Scraper command from the API
- **WHEN** an administrator triggers a manual scrape
- **THEN** the API SHALL send the command to the scraper with the `x-internal-key` header

### Requirement: Pooled HTTP Clients for Per-tenant Models
Per-tenant chat clients and the fallback model SHALL be built by `IChatModelFactory` (Infrastructure) over the `IHttpClientFactory` named client `llm`. Code in the Application and API layers SHALL NOT instantiate `HttpClient` or HTTP handlers. The platform `Kernel` and the keyed `IngestionKernel` are built in Infrastructure with their own HTTP clients (the OpenAI-compatible ingestion client comes from the named client `IngestionClient`).

#### Scenario: Many sequential chat requests
- **WHEN** many chat requests of a tenant using `google`, `openai` or `openrouter` are processed
- **THEN** their HTTP connections SHALL come from the `llm` handler pool instead of one new `HttpClient` per request

### Requirement: Embedding Generator Resolution
Retrieval SHALL resolve the embedding generator from the platform `Kernel`, configured by `Ai:Embeddings:*` (provider `ollama` by default, or `google`, `openai`, `openrouter`), never from a per-tenant chat client.

#### Scenario: Non-streaming completion with a user message
- **WHEN** `GetCompletionAsync` is called with a non-empty user message
- **THEN** the query embedding SHALL be generated with the platform embedding generator
- **AND** the result SHALL be `Success = true` with the answer text and an empty source list (sources are only cited inside the answer)
